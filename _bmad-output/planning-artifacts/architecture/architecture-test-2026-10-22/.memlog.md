- (decision) 设计范式=管道-过滤器：意图→路由→缓存→生成→审核→组装→下发每跳为独立过滤器，经标准化消息信封传递；绑定首响链路全部处理 hop，防止过滤器间私有耦合
- (assumption) [ASSUMPTION] MVP 流量规模按微聊全量设计（百万级 QPS 链路旁路接入），无法按小流量简化缓存/会话设计
- (question) 过滤器实现形态未决：全图 LangGraph 编排 vs 热路径手写+LLM 子图 LangGraph。待评审决策。
- (decision) 过滤器实现形态=手写热路径（意图/缓存/审核/组装，毫秒级可控）+ LLM 生成节点为 LangGraph 子图；绑定意图分类 P99<50ms 与缓存命中 80ms 预算，防止图调度开销侵蚀延迟 SLO
- (decision) 会话状态单写者：仅会话管理模块可写会话状态；过滤器只读并传 session_id；追问计数等并发写用 Redis 原子操作/分布式锁。防止两个过滤器各自写状态导致竞态与状态变更点发散
- (question) 路由决策点形态未决：每条消息单一分类后路由（单意图假设，简单）vs 一消息多意图扇出并行通道（完备但复杂）。倾向前者。待评审确认。
- (decision) 路由形态=单意图路由：每消息单一意图标签+置信度→唯一通道（缓存/LLM/转人工）；多意图扇出推迟至 V2+
- (decision) 审核超时视为不通过→模板兜底；超时阈值待压测调优（约束 P99<3s 不超时）
- (question) L1 缓存层角色未定义：PRD 仅述 L0 语义，L1 为本地缓存层，需澄清是 L0 前置（会话级热点）还是 Caffeine 仅作 Redis 客户端缓存。倾向前者。待评审澄清。
- (decision) L1=Caffeine 进程内缓存，存会话级热点（最近意图/追问计数/会话事实快照）；L0=Redis 分布式事实卡片缓存。查找顺序 L1→L0→LLM；支撑 80ms 缓存命中预算并减少对 Redis 往返
- (decision) 事实卡片数据源以 Kafka 事件为唯一写入路径；Redis 缓存仅作读副本由事件消费者更新/失效；防止 DB 与缓存双写不一致
- (decision) 转人工集成=Agent 经 Kafka 发转交指令给既有 SpringBoot 经纪人工作台（单向指令，复用现有消息链路）；避免 Python 侧重建双向 IM 连接
- (question) 部署拓扑未定：K8s vs 公司 PaaS；实例水平扩展与可用区冗余未指定。骨架将以占位符标注待运维/架构评审决策，不臆断具体平台。
