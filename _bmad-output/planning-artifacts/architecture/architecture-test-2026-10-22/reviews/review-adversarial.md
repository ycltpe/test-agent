# 对抗性评审 — AD-11 指代消解 & AD-1 信封增补专项

## 评审方法

针对本次 PRD 新增 FR-11 引出的两处脊柱改动（AD-11 前置过滤器、AD-1/一致性约定的信封三字段），构造"下一层单元"思想实验：为每个风险点给出两个各自逐字遵守全部 AD、却产出互不兼容制品的具体实现（过滤器 A vs 过滤器 B、生产者 vs 消费方、写路径 X vs 写路径 Y）。无法排除这种构造的缝隙即判定为脊柱缺陷，按"能否导致线上事故/合规事故"排序。

本轮攻击面：coref 元数据的权威 schema 归属、resolved_message 的精确文本形态与可见性边界、追问判定的比较口径、coref 持久化的写/读路径、trace 与风控审核的双文本口径。

---

## 构造一：coref 字段 —— 同一个信封槽位，两种不可解析的 schema

**触及 AD：** AD-1（信封单一 Pydantic 模型）、AD-11（coref = "引用元数据：引用实体类型、实体 ID"）、一致性约定（"Redis 值用 JSON 序列化"）

AD-11 对 coref 的定义只有一句话："引用实体类型、实体 ID"。这句话没有回答：**单引用还是多引用？字段名是什么？是否含 span / 原文片段 / 置信度？** 而 coref 的消费方至少有三个：会话管理模块（要把它序列化进 Redis）、风控审核（要判断生成是否锚定正确实体）、Langfuse trace（要可审计）。信封是"单一 Pydantic 模型"，但脊柱没有给出 coref 子模型的权威定义——一致性约定表只钉死了信封顶层字段名，coref 的类型是 `CorefRef | None` 还是 `list[CorefRef] | None`，无人裁决。

两个都守规矩的团队：

- **团队 A（指代消解过滤器）**：实现为 `coref: {"entity_type": "house", "entity_id": "xxx"}`——扁平单引用，因为 AD-11 说"引用实体类型、实体 ID"（单数口径），且"消解锚定会话单一房源"。
- **团队 B（会话管理模块）**：按"非房源实体指代（价格、楼层、位置等）尽力消解"理解为多引用，实现为 `coref: {"refs": [{"type": "house", "id": "xxx"}, {"type": "price", "id": null}]}`——列表口径，因为一条消息可以同时指代房源和价格（"它的总价呢"）。

序列化侧各自合法（"Redis 值用 JSON 序列化"对任何 JSON 都成立），消费侧立刻断裂：风控审核团队 C 写 `coref["entity_id"]` 对 B 的 schema 抛 KeyError → 命中一致性约定的"所有过滤器异常降级至模板兜底" → 每条多引用消息都吃到无信息兜底文案；反过来若 C 写 `coref["refs"][0]`，A 的 schema 同样炸。**在 AD-11 里"多引用场景"没有排除的情况下，两种实现无法共存，而脊柱没有提供仲裁依据。** 即便两边侥幸对齐字段名，`entity_id` 的取值口径仍未定：团队 A 填业务主键 `house_id`，团队 B 填内部索引 ID——事故的种子。

**判级：P0。** 闭合方式：在 AD-11 或一致性约定中新增 `CorefRef` 权威 Pydantic 子模型（字段清单、多引用列表形态、entity_id 一律为业务 house_id 或明确 ID 空间），并声明信封模型即唯一真相源，下游禁止自定义解析。

## 构造二：resolved_message 的"自包含"格式 —— 内联标注 vs 纯文本替换，三个消费方各自合法地发散

**触及 AD：** AD-11（"输出 = 消解后消息（自包含文本，如'它多少钱' → '这套房（house_id: xxx）多少钱'）"）、AD-1（信封字段无可见性/序列化边界）、AD-10（身份披露与禁用表述）

AD-11 给了 resolved_message 的唯一示例：把 house_id **内联标注进自然语言文本**。但这个示例的效力没有上升为 Rule：Rule 只说"输出消解后消息（自包含文本）"。于是"自包含"存在两种互不兼容的合法实现：

- **实现 A（内联标注派）**：严格按示例，resolved_message = `"这套房（house_id: 12345）多少钱"`——标注嵌入文本。
- **实现 B（替换派）**：resolved_message = `"这套房多少钱"`——纯自然语言替换，实体 ID 只放 coref 字段（构造一里两个团队已经证明 coref 本身无定形）。

现在让三个下游团队各自独立实现，全部逐字遵守 AD：

- **追问判定团队**：消费 resolved_message 做跨轮比对。A 派文本含 house_id，B 派不含；同一买家会话在两种实现下的比对文本不同 → 追问计数漂移（叠加构造三的口径问题，见下）。
- **LLM 生成团队**：prompt 里嵌入 resolved_message。A 派 prompt 含内部 ID 标注，模型可能学着在生成文本里复述 `house_id: 12345`；风控审核的范围（AD-10）只管"我是这套房的经纪人"类表述，管不住 ID 标注泄漏 → **买家看到内部主键**，合规事故。
- **响应组装/兜底团队**：AD-1 信封没有给字段标注可见性边界。团队 X 的模板从 `envelope.resolved_message` 取买家可见文案（"信封是过滤器间唯一载体，直接用最新字段很自然"）；团队 Y 坚持用 `envelope.message`。X 的买家看到"这套房（house_id: 12345）多少钱"式内部标注；且两种模板在风控审核眼里输入文本不同，审核口径分叉。

两个实现都在 AD-11 字面之内（示例 vs "自包含"的宽松读法），但它们在下游汇合时产生：**追问判定不一致 + LLM 泄漏内部 ID + 买家可见文本分叉 + 审核输入分叉**，四条事故路径共用同一个根：resolved_message 的精确格式与"仅限管道内部消费、不得进入买家可见面"的边界从未成为 Rule。

**判级：P0。** 闭合方式：AD-11 Rule 增补——(1) resolved_message 格式定为唯一规范（建议：纯自然语言替换 + house_id 仅经 coref 传递，内联标注示例降级或删除）；(2) 新增可见性 Rule：resolved_message 为管道内部表示，禁止进入下发适配器与任何买家可见文案；响应组装仅消费 message（或显式声明的展示字段）。

## 构造三：追问判定 —— "只消费消解后消息"字面强制文本比对，与 FR-2 标签级判定直接矛盾

**触及 AD：** AD-11（"意图分类（FR-1）、重复追问判定（FR-2）、LLM 生成（FR-6）只消费消解后消息，禁止直接读取买家原始文本"）、AD-3、FR-2 可验收口径

这是本轮最锋利的一刀，因为它不是"遗漏"，而是 **AD-11 的 Rule 字面与 PRD 的可验收口径互相矛盾**，两个忠实执行者必然有一个出局。

FR-2 的可验收口径："同一意图判定基于消解后消息：指代与同义改写叠加的场景（'它多少钱'与'这套房多少钱'）视为同一意图；同义改写视为同一意图（'还在吗'与'没卖掉吧'）"。注意前半句的语义：判定落点是"同一意图"，不是"同一文本"。而 AD-11 说追问判定"只消费消解后消息"——没有提意图标签。

两个逐字守 AD 的团队：

- **团队 A（文本派）**：严守"只消费消解后消息"，实现为对 resolved_message 做相似度比对。考虑 AD-11 自己的降级条款："无法确定先行词时保留原文进入意图分类"——轮 1 买家说"它多少钱"，此时会话无先行词，resolved_message = 原文 "它多少钱"；轮 2 买家说"这套房多少钱"，resolved_message = "这套房（house_id: xxx）多少钱"（或构造二的 B 派 "这套房多少钱"）。文本比对下两轮的相似度远低于任何阈值，**指代叠加追问被判为不同消息 → 计数器清零或分流 → "同一意图追问 ≥3 次 100% 转人工"（FR-3）在指代场景下结构性失效**。而 FR-2 恰恰要求这个场景 ≥95% 判同。更糟：纯文本比对对"还在吗"/"没卖掉吧"这类零词面重叠的同义改写天然无解，FR-2 的 95% 指标从架构层面不可达。
- **团队 B（标签派）**：读出 FR-2 的真实意图，实现为读取会话状态中各轮的意图标签（AD-4 允许过滤器只读会话状态），比较"同一 intent 标签 + coref 锚定同一 house_id"。行为正确——但它消费的已不只是"消解后消息"，还有会话状态的意图历史。**若评审时以 AD-11 的 Rule 字面为准，B 的实现对"只消费消解后消息"构成违规争议；以 FR-2 口径为准，A 的实现构成交付物不合格。** 脊柱把仲裁责任推给了施工期，这就是洞。

根因：AD-11 把"禁止读原始文本做消解"（合理）误写成"只消费消息文本"（过强：堵死了唯一可行的标签级判定路径），而 FR-2 的真实需求是"消费意图标签 + coref 实体锚定"。

**判级：P0。** 闭合方式：AD-11 Rule 改写为分层口径——下游禁止读取买家原文做消解；追问判定消费"意图标签（经会话状态读取）+ coref 实体锚定"，并显式声明文本相似度比对不构成 FR-2 的合规实现；同时补一条追问计数的权威 key 与重置语义（上轮评审遗留，本轮确认与 coref 口径耦合，必须同批闭合）。

## 构造四：coref 持久化 —— 信封 coref 与 Redis coref:{turn} 两个真相源，AD-4 的"只读"条款合法化了双读路径

**触及 AD：** AD-11（"消解结果由会话管理模块写入会话状态（Redis），键 weiliao:session:{session_id}:coref:{turn}"）、AD-1（过滤器仅通过信封传递）、AD-4（"过滤器只读并传 session_id"）、AD-7（转人工原子终态）

AD-11 让 coref 同时存在于两处：信封字段（过滤器间传递）和 Redis coref:{turn}（会话状态）。哪个是真相源？读路径是什么？三个独立的合法构造给出三个答案：

- **读路径 X（信封派）**：下游全部消费 envelope.coref。Redis coref:{turn} 是一次**写后无读的合规死写**——FR-11 的可验收口径"消解结果写入会话状态（Redis）"被字面满足，但没有任何运行时消费者；它的唯一消费者是未来 V2 功能。这本身不是事故，但它意味着 coref:{turn} 的 schema（构造一）从未被任何运行时代码校验过——团队 A/B 的 schema 分歧可以潜伏到 V2 才爆炸。
- **读路径 Y（Redis 派）**：某下游（如追问判定团队 B，构造三）按 AD-4"过滤器只读会话状态"从 Redis 读 coref:{turn} 而非信封字段。**这在 AD 字面下完全合法**——AD-4 明确允许过滤器只读会话状态，AD-1 只禁止"跨过滤器直接函数调用"，读共享 Redis 不算函数调用。现在信封 coref 与 Redis coref:{turn} 出现两个并行真相源：指代消解过滤器产出后，会话管理模块何时持久化（每过滤器 hop 同步写？管道末批写？）脊柱未定义。写时机团队 P 选"hop 即写"，团队 Q 选"管道末批写"——管道中途崩溃时，P 留下 coref 持久化而 intent 未写，Q 什么都不留；**追问判定在重放/补偿路径下读到两套不同的历史**。
- **写时机 Z（终态分支派）**：消息走转人工分支（红线意图恰好以指代形式出现："它的底价还能谈吗"）。AD-7 说转人工分支是原子终态出口、禁止回流；AD-11 说 coref 由会话管理模块写。**该轮 coref 写不写？** 团队 R：写（经纪人工单需要完整上下文，且 trace 审计要可重建）；团队 S：不写（终态分支绕过主链，会话管理模块只在主链回调时持久化）。两边都通得过 AD-7 + AD-11 的字面评审。后果：SM-6（转人工判定准确率）审计时，对指代型红线消息，一种实现能重建"消解→红线→转人工"链条，另一种实现 trace 里 coref 缺失，**审核员无法判定转人工是否正确**——而 SM-5/SM-6 的验收口径恰恰以 Langfuse trace 数据为准。

**判级：P1（转人工场景升 P0）。** 闭合方式：AD-11 Rule 增补——(1) 信封 coref 为运行时唯一真相源，Redis coref:{turn} 为异步落盘副本，禁止下游从 Redis 反读做运行时决策（收紧 AD-4 的"只读"条款，枚举只读白名单）；(2) 会话管理模块持久化时机定为"信封 hop 同步"或"管道末"，二者择一并写明崩溃语义；(3) 明确转人工分支各轮 coref/intent 的持久化义务（建议：终态前强制落盘，作为工单上下文一部分）。

## 构造五：trace 与风控审核的双文本口径 —— message 还是 resolved_message，验收数据源没有唯一答案

**触及 AD：** 一致性约定（"Langfuse trace_id 贯穿全链路"、"SM-5/SM-6 验收口径以 Langfuse trace 数据为准"）、AD-8（风控审核）、AD-11（消费方枚举）

信封现在携带两个文本：买家原文 message 与消解后 resolved_message。一致性约定的可观测条款只说"trace_id 贯穿全链路"，**没有规定 trace 里记录哪个文本、coref 是否入 trace**。而 AD-11 列举的"只消费消解后消息"的名单是：意图分类、重复追问判定、LLM 生成——**风控审核不在名单内**。这留下两个各自合法的团队：

- **团队 M（原文派）**：风控审核消费 `envelope.message`。理由充分：审核对象是"买家实际说了什么"，红线词（议价、投诉暗示）以原文为准；AI 生成文本要与真实输入对账。
- **团队 N（消解派）**：风控审核消费 `envelope.resolved_message`。理由同样充分：AD-11 的精神是"全链路统一口径"，且构造二 A 派实现下 resolved_message 含 house_id 锚定，审核"生成内容是否锚定正确房源"必须看它；且 AD-10 的禁用表述检测在原文上可能因指代形式漏判（"它的底价呢"在原文里不含房源词）。

两个团队都通得过评审。后果不止审核逻辑分叉：**SM-5/SM-6 以 Langfuse trace 为准验收**——团队 M 的 trace 存原文，团队 N 的 trace 存消解文本，两份 trace 对同一消息给出不同的可审计记录；回放评测、badcase 复盘、合规取证时，"系统当时到底依据哪个文本做的决策"在 trace 里不可重建（尤其叠加构造四的 coref 落盘分叉）。同理，LLM 生成的成本/token 追踪（一致性约定·可观测）记录的 prompt 是哪一个版本，两个团队答案不同。

附带变体：AD-8 的审核超时兜底切换，切换事件的 trace 要不要同时记录两个文本 + coref 快照？不定的话，超时兜底后的 badcase 无法归因到"消解错了"还是"审核慢了"。

**判级：P1。** 闭合方式：一致性约定·可观测增补——Langfuse 每个 hop 的记录必须同时携带 message、resolved_message、coref 快照（三字段全量，不得择一）；风控审核的输入字段在 AD-8 或新 AD 中显式钉死（建议：审核输入为 message + resolved_message 双文本 + coref，红线词检测跑原文、锚定一致性检测跑消解文本）。

## 汇总

| # | 构造 | 根因 | 判级 | 闭合方式 |
| --- | --- | --- | --- | --- |
| 1 | coref schema 两派互不解析 | coref 无权威子模型，"实体类型+ID"未操作化 | P0 | 钉死 CorefRef Pydantic 模型 + ID 空间 |
| 2 | resolved_message 内联标注 vs 纯替换 | 示例未升级为 Rule；信封字段无可见性边界 | P0 | 定唯一格式 + 禁入买家可见面 |
| 3 | 追问判定文本派 vs 标签派 | AD-11"只消费消解后消息"与 FR-2 标签级口径矛盾 | P0 | AD-11 分层改写：禁原文消解，追问判定走标签+锚定 |
| 4 | coref 信封 vs Redis 双真相源 | 读路径/写时机/终态分支持久化未定义 | P1（转人工场景 P0） | 信封为唯一运行时真相源 + 落盘时机 + 终态强制落盘 |
| 5 | trace/风控的 message vs resolved_message 双口径 | 观测条款未定文本字段；审核不在 AD-11 消费名单 | P1 | 观测三字段全量；审核双文本输入钉死 |

**总判定：needs-work。** 三处 P0 全部集中在 AD-11 新增内容的"接口定语"层面——过滤器的位置、延迟、降级都说清了，但它产出的两个工件（resolved_message 的精确格式、coref 的精确 schema）以及一个消费方（追问判定）的比较口径，均处于"两种合法实现互不兼容"状态。建议以"AD-11 增补三条 Rule + 一致性约定增补 CorefRef 模型与观测三字段"的最小补丁闭合，无需改动管道结构本身。
