## Findings（按严重度分级）

### P1 — 会让下一层单元不兼容分叉

**F1. 追问计数同时被声明为 L1 内容与 Redis 原子计数，多实例下必然分叉。**
AD-5 规定 L1（cachetools.TTLCache，进程内）"仅存会话级热点（最近意图、追问计数、handoff 状态快照）"；而 AD-4 规定"追问计数自增用 Redis 原子操作"，FR-2 要求计数器存 Redis、FR-10 要求多实例读到一致状态。两种读法会产生不可兼容的实现：
- 读法 A：L1 中的追问计数是 Redis 计数的进程内缓存副本 → 单写者/失效策略未定义，TTL ≤30s 与"会话 TTL 30 分钟"叠加会导致计数回退，≥3 次硬触发（FR-3）漏判；
- 读法 B：L1 计数是权威值 → 多实例部署（Deferred 中部署拓扑未定，但逻辑架构已声明实例无状态、任意实例可处理任意消息）下每个实例各自计数，FR-2/FR-10 直接违反。

修复方向（供参考，不在本评审中修改脊柱）：在 AD-5 明确"追问计数权威值仅存 Redis，L1 不缓存计数"或"L1 副本 + 每次自增穿透 Redis，L1 仅读加速且允许短暂不一致、硬触发判定一律以 Redis 为准"。

**F2. 硬触发条件的评估无归属过滤器，"图片/语音输入"路径完全缺失。**
管道图有 `D{硬触发?}` 判定节点，但没有任何 AD 或 Consistency Convention 说明**哪个过滤器、依据什么数据**评估硬触发。PRD FR-3 的硬触发全集为：红线意图（分类器输出）、图片/语音输入、同意图追问 ≥3 次（Redis 计数）、负面词汇命中（词库来自 OQ-3，owner 未定）。其中：
- 图片/语音输入 100% 转人工（FR-3 testable consequence）在脊柱中无任何落点——信封字段 `message` 标注为"买家原文"文本，多媒体消息的接入、信封表达、转人工路径均未定义；
- 负面词汇命中由哪个过滤器评估、词库从哪里加载、是否依赖 OQ-2 的本地敏感词前置层，均无说明。

两个单元各自实现时，一个会把硬触发评估放进意图分类过滤器，另一个会新建硬触发过滤器，信封与路由行为不兼容。另注意 OQ-2（风控中台 QPS 上限、是否引入本地敏感词缓存前置层）是架构相关的开放问题，但脊柱既未决定也未列入开放问题（见 F5）。

### P2 — 重要但可在下一层补

**F3. AD-3 的"多意图场景拆分为多次独立消息处理"规则不可执行。** 单条消息无法被"拆分为多次独立消息"——是复制信封并行处理？还是丢弃次要意图？还是只取 top-1？该规则声称防止"多意图扇出导致响应聚合复杂化"，但规则文本本身留下的自由度正是它所声称防止的分叉。建议改为可判定的规则，如"意图分类输出 top-1 即丢弃其余候选，单信封单意图贯穿管道"。

**F4. AD-9 的 OpenAI 超时阈值（1.8s）与 PRD FR-8（>3s）不一致，且 PRD §4.4 标题"双审核"与正文（仅后置审核）矛盾，脊柱未消解。** 1.8s 更严格、不会导致 FR-8 验收失败（>3s 超时必然先触发 1.8s 切换），但作为 spec 驱动的脊柱应与 PRD 显式对齐或注明"严于 spec 的有意决策"。另外 PRD §4.4 Description 称"生成前后均须过风控审核"，FR-7 正文却只有后置审核；脊柱只落地了后置审核（AD-8），若"生成前审核"真实存在，会改变管道（prompt 需先过审）——脊柱应显式声明该歧义的存在并选边或列为开放问题。

**F5. 开放问题承接不全（清单第 6 项）。** OQ-1（意图分类器选型）与 OQ-5（消解实现选型）已正确进入 Deferred；但 OQ-2（风控 QPS → 本地敏感词前置层）是架构维度（是否新增一个过滤器级组件）却未出现在 Deferred 或任何 AD 中；OQ-3（负面词汇词库 owner）影响硬触发过滤器的词库加载来源。两者均应按"决定 / 推迟 / 开放问题"三态之一显式落位。

**F6. 部分 testable consequence 无架构落点（清单第 5 项的残余缺口）。**
- FR-5"LLM 响应与首次缓存响应文本相似度 < 0.8"：没有任何 AD 约束 LLM 生成的去重（如 prompt 注入"不得重复首次应答"或组装层校验）；
- FR-6"首 token P99 < 1.5s"：AD-9 只有端到端 ≤1.8s 预算，未分解出首 token 子预算；
- FR-10"会话过期后重新发起对话状态从零初始化"：AD-4 未声明会话 TTL（30 分钟，PRD/OQ-4）与过期初始化语义；
- FR-1/FR-11 的准确率指标（≥90%/≥95%）依赖第 4 周测试集，脊柱无任何评估 harness/离线评测管道落点——非阻塞，但建议在 Consistency Conventions 的"可观测"或 Deferred 中补一条评测出线的约定，否则两个单元对"在哪跑标注评测"会分叉。

### P3 — 提示级

**F7. 技术版本无法在本环境独立复核（清单第 4 项）。** Stack 表声称"截至 2026-10-22 经 PyPI 核实"。本次评审运行于离线沙箱，无法联网复核 FastAPI 0.159.1 / Uvicorn 0.54.0 / Pydantic 2.14.1 / LangChain-OpenAI 1.7.2 等"最新版"声明。表内格式规范（下限约束 + 核实注记 + API 级模型名与采购挂钩）本身合理，采纳为"声称已核实、未独立复核"。LangGraph 1.2.16、redis-py 8.1.0、Langfuse 5.0.4、cachetools 7.2.4 为钉死版本，建议在技术设计层确认与 Python ≥3.11 的兼容性矩阵。

**F8. AD-4 的"单写者"规则与 L1 快照写入者未对齐。** AD-5 说 L1 存"handoff 状态快照"，但谁是 L1 的写入者未声明（会话管理模块还是各过滤器自写 L1？）。若过滤器各自读写进程内 L1，"过滤器只读会话状态"的规则就被架空。建议在 AD-5 补一句"L1 由会话管理模块统一读写，过滤器经会话管理模块访问"。
