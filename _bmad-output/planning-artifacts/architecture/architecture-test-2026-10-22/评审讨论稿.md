## 一、已收敛决策（供确认）

以下决策已在架构推演中确认，如委员会有异议请逐项提出：

| # | 决策 | 理由 | 状态 |
|---|------|------|------|
| 1 | 设计范式：管道-过滤器 | LangGraph 图本身即管道；每 hop 独立可替换，满足毫秒级延迟预算 | 待确认 |
| 2 | 热路径手写，LLM 子图 LangGraph | 意图分类 P99 < 50ms、缓存命中 80ms，全图 LangGraph 调度开销不可接受 | 待确认 |
| 3 | 单意图路由（非多意图扇出） | MVP 9 类意图足够；多意图扇出复杂度与延迟不可控 | 待确认 |
| 4 | 会话状态单写者 + Redis 原子操作 | 防止多过滤器并发写状态导致竞态 | 待确认 |
| 5 | L1 = Caffeine 会话热点前置层；L0 = Redis 事实卡片分布式缓存 | L1 减少对 Redis 网络往返，支撑 80ms 缓存命中预算 | 待确认 |
| 6 | 事实卡片以 Kafka 事件为唯一写入路径 | 防止 DB 与缓存双写不一致 | 待确认 |
| 7 | 转人工 = Kafka 单向指令给 SpringBoot 经纪人工作台 | 复用现有消息链路，避免 Python 侧重建双向 IM 连接 | 待确认 |
| 8 | 风控审核超时视为不通过 → 模板兜底 | 保障 P99 < 3s 不超时，服务不中断 | 待确认 |
| 9 | OpenAI 故障自动降级 + 10% 步进恢复 | 满足 99.95% 可用性 SLO | 待确认 |
| 10 | AI 身份披露为硬约束 | 合规要求，Agent 响应 100% 携带 AI 标识 | 待确认 |

## 二、待对齐开放问题（会上重点讨论）

### Q1：意图分类器选型（阻塞模型层指标验收）

- **背景**：PRD OQ-1 明确选型未决，依赖语料标注进度（第 2 周）。
- **选项**：
  - A. 规则引擎（零成本、零延迟，但覆盖有限，准确率天花板低）
  - B. gpt-4o-mini zero-shot（快速上线，但受 OpenAI 配额约束，与缓存拦截率目标存在资源竞争）
  - C. 微调小模型（准确率天花板高，但标注与训练周期长，MVP 8-10 周存在延期风险）
- **建议**：MVP 先采用 B（gpt-4o-mini zero-shot）作为 baseline，同步推进语料标注；若第 2 周标注进度达标且准确率不足 90%，启动 C 的评估。
- **会上需决策**：是否同意上述分阶段策略？微调小模型的训练资源与标注人力是否已落实？

### Q2：L1 缓存角色与拦截率口径

- **背景**：PRD 提及 L0/L1 两级缓存但未定义 L1 角色；缓存拦截率目标 80% 需明确统计口径。
- **关键问题**：
  - L1 是否仅作为 L0 的前置（会话级热点），还是允许缓存部分事实卡片？
  - 拦截率 80% 的计算基数：仅首次消息，还是包含重复追问？（重复追问强制走 LLM，会拉低拦截率）
- **建议**：L1 仅缓存会话级热点（最近意图、追问计数、会话事实快照），不缓存事实卡片；拦截率基数仅统计首次消息（重复追问不计入分母）。
- **会上需决策**：上述口径是否可行？L1 的 TTL（建议 ≤ 30s）是否合理？

### Q3：Kafka 数据流拓扑细节

- **背景**：PRD 明确 `house.sync.trigger` 事件触发缓存失效，但未定义完整 topic 清单与分区策略。
- **待明确**：
  - 买家消息接入 topic（现有微聊链路是否已有可用 topic？）
  - 转人工指令 topic（是否与现有经纪人工作台消息 topic 复用？）
  - 事实卡片更新 topic（`house.sync.trigger` 的频率与峰值 QPS）
- **建议**：接入与转人工优先复用现有 topic；事实卡片更新 topic 由房源服务团队确认峰值。
- **会上需决策**：现有 topic 的可用性与峰值容量评估由谁负责？何时给出结论？

### Q4：风控审核超时阈值与降级策略

- **背景**：AD-8 规定超时视为不通过，但具体阈值未调优。
- **关键问题**：
  - 风控中台 P99 延迟多少？超时阈值设为多少才能同时满足"审核通过 ≥ 95%"与"P99 < 3s"？
  - 超时后是否允许重试一次（可能超 3s），还是直接切换模板？
- **建议**：超时阈值初始设为 500ms（待压测调优）；超时后直接模板兜底，不重试。
- **会上需决策**：风控中台能否提供 P99 延迟承诺？500ms 阈值是否可接受？

### Q5：部署拓扑与容量规划

- **背景**：架构脊柱未指定部署平台（K8s vs 公司 PaaS）、实例水平扩展策略与可用区冗余。
- **已明确约束**：逻辑架构保持实例无状态、任意实例可处理任意消息；L1 缓存仅为优化层，不影响正确性。
- **待明确**：
  - 峰值 QPS 估算（微聊全量 vs 灰度阶段）
  - 实例水平扩展的触发条件（CPU/内存阈值）
  - 是否跨可用区部署（满足 99.95% 可用性）
- **建议**：MVP 灰度阶段单可用区部署，全量前完成跨可用区部署；容量按峰值 QPS 的 2 倍预留。
- **会上需决策**：运维团队能否在 MVP 第 4 周前给出部署拓扑与容量规划？
