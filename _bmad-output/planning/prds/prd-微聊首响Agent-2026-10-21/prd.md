# PRD: 微聊首响 Agent

## 0. Document Purpose

本文档面向微聊首响 Agent 的实现团队（算法工程师、后端工程师、风控对接人）及技术评审委员会。PRD 基于已批准的 Product Brief（`brief-微聊首响Agent-2026-10-21/brief.md`）展开，Brief 中的范围声明、成功指标与风险条目在本文档中转为可验收的功能需求（FR）与非功能需求（NFR）。

Brief 决策已全部继承：MVP 仅 OpenAI + 模板兜底（无多级降级）、仅硬触发转人工、AI 身份明确披露、缓存拦截率目标 80%。实现方案（LangGraph 架构、L0/L1 缓存设计、Kafka 拓扑、虚拟 key 方案）见独立技术设计文档，不在本文档重复。

---

## 1. Vision

安居客微聊链路中，买家首次消息的平均真人响应时间为分钟级，夜间及高峰时段可达小时级，直接流失高意向客户。微聊首响 Agent 在买家消息到达后 **3 秒内**给出准确、合规的首次响应，**完全替代真人首响**，仅在命中预设红线条件时转交经纪人。

MVP 不追求"最聪明的 Agent"，追求"最快、最稳、最守规矩的 Agent"：80% 的高频问题由缓存与模板在零 LLM 调用下应答，剩余 20% 由 LLM 受控生成，任何故障场景均可降级至模板应答，服务不中断。

## 2. Target User

### 2.1 Jobs To Be Done

- **买家（JTBD-1）**：作为正在浏览房源的买家，我想在发消息后立即知道房子是否还在、价格多少，而不是等一个可能永远不来的回复
- **经纪人（JTBD-2）**：作为同时接待多位客户的经纪人，我想让系统帮我挡掉"在吗""什么价"这类重复问答，让我把时间花在真正能成交的沟通上
- **平台（JTBD-3）**：作为平台方，我想确保所有价格、学区等敏感问题的回答口径统一、合规，不因个别经纪人的表述问题产生监管风险

### 2.2 Non-Users (v1)

- 发起议价、合同条款咨询的买家（直接转人工，不由 Agent 处理）
- 需要房源图片/视频解读的买家（v1 不处理图片输入，转人工）
- 经纪人本人不是本系统的直接用户，是转人工后的接收方

### 2.3 Key User Journeys

**UJ-1. 买家小李在晚上 10 点问"这套房还在吗"，3 秒内收到回复。**
小李白天上班，晚上刷安居客看到一套合适的房子，发消息问状态。系统识别为首次询问，查 L0 缓存命中（该房源 5 分钟内已被问过），直接返回："在的，挂牌 385 万，对口实验小学。" 全程无 LLM 调用，响应时间 80ms。小李满意，继续问"能便宜吗"——系统识别为议价意图（红线），转人工，提示经纪人跟进。

**UJ-2. 买家小王连续追问同一问题，第二次收到不一样的回复。**
小王 5 分钟前问过"这套房还在吗"，收到答复后又问了一遍（可能是没看清，可能是不放心）。系统识别为**重复追问**（turn ≥ 2），不走缓存，由 LLM 结合对话上下文生成安抚性回应："放心，还在的，您是想约时间看看吗？我可以帮您登记。" 随后小王追问"它采光怎么样"——指代消解先将"它"归一化为当前房源引用，再分类为房源咨询进入 LLM 链路，回复始终围绕同一套房子。同时系统为该房源添加"用户关注"标记，经纪人上班后可见。

**UJ-3. 买家小张问"这房支持公积金贷款吗"，系统转人工。**
小张的问题涉及贷款政策（红线类型），系统不生成回答，立即触发转人工流程，消息进入经纪人工作台，同时通知小张："这个问题已转给经纪人，稍后回复您。" 转人工延迟 P99 < 5s。

**UJ-4. OpenAI 配额耗尽，系统无缝切换到模板应答。**
高峰期 OpenAI 返回 429，系统自动切换至模板引擎，买家收到的响应从 LLM 生成变为模板组合，格式不变，服务无中断。监控告警触发，运维介入。

## 3. Glossary

- **首次消息（First Message）** — 买家在一个房源会话中发出的第 1 条文本消息。系统对首次消息进行意图识别并生成首响。
- **重复追问（Follow-up Query）** — 同一买家在同一房源会话中，针对同一意图发出的第 2 次及以后的消息。重复追问必须走 LLM，不得走缓存（避免机械化重复）。
- **意图（Intent）** — 系统对买家消息的分类结果。MVP 意图集：GREETING / PRICE_INQUIRY / AVAILABILITY / LOCATION / PHOTO_REQUEST / NEGOTIATION（红线）/ LOAN_POLICY（红线）/ COMPLAINT（红线）/ UNKNOWN。
- **红线意图（Red-line Intent）** — 必须转人工、禁止 Agent 生成回答的意图类型。MVP 红线集：NEGOTIATION / LOAN_POLICY / COMPLAINT。
- **硬触发（Hard Trigger）** — 无需置信度判断、命中即转人工的确定性规则。MVP 硬触发条件：红线意图、图片/语音输入、同一意图追问 ≥ 3 次、负面词汇命中。
- **转人工（Human Handoff）** — 将会话控制权移交经纪人工作台的过程，包含消息转发和经纪人通知两个动作。
- **L0 缓存（L0 Cache）** — 以"意图 + 房源 ID + 房源状态 + 价格分桶"为 key 的应答缓存。存储单元是**事实卡片**（房源状态、价格、关联信息），不是最终文案，由模板引擎或 LLM 在消费时组装。
- **模板兜底（Template Fallback）** — 当 LLM 不可用时，由预定义模板 + 事实卡片拼装应答的降级模式。
- **AI 身份披露（AI Disclosure）** — 聊天界面中向买家明示"当前由 AI 助手回复"的标识，不得以任何形式伪装真人经纪人。
- **会话（Session）** — 买家与某套房源的一次连续对话，以 session_id 标识，超过 30 分钟无消息自动过期。
- **首响延迟（First Response Latency）** — 从买家消息到达系统到买家收到响应的端到端耗时。
- **指代消解（Coreference Resolution）** — 系统在意图分类之前执行的预处理步骤：将会话上下文中已知的实体引用（"它""这套""那套""上面说的"等）归一化为显式实体引用，输出自包含的消解后消息。由于每个会话绑定单一房源，先行词在绝大多数场景下可由会话状态确定，消解的核心是归一化而非开放式实体链接。
- **消解后消息（Resolved Message）** — 指代消解的输出：将原始消息中的指代替换为显式实体引用后的完整文本，是意图分类、重复追问判定与 LLM 生成链路的唯一输入。

## 4. Features

### 4.1 指代消解

**Description：** 买家消息中的房源引用常以指代形式出现（"它""这套""那套""上面说的"），单看原始文本无法稳定分类——"它多少钱"缺少分类所需的主语。系统在意图分类之前执行指代消解，注入会话上下文中已知的房源引用，输出自包含的消解后消息，使意图分类、重复追问判定与 LLM 生成均无需回溯对话历史即可正确工作。

**Functional Requirements：**

#### FR-11: 指代消解

系统对每条买家文本消息，在意图分类之前执行指代消解，输出消解后消息与引用元数据（引用实体类型、实体 ID）。

**Consequences (testable):**
- 房源指代（它/这套/那套/上面说的 等）消解准确率 ≥ 95%（人工标注测试集，含指代类样本 ≥ 20%，与 FR-1 测试集同期建设）
- 消解输出为自包含文本（如"它多少钱" → "这套房（house_id: xxx）多少钱"）；意图分类（FR-1）、重复追问判定（FR-2）与 LLM 生成（FR-6）只消费消解后消息，不直接读取买家原始文本
- 消解延迟 P99 < 10ms；FR-1 的意图分类延迟预算（P99 < 50ms）口径明确为含消解的端到端
- 消解结果写入会话状态（Redis），键：`weiliao:session:{session_id}:coref:{turn}`
- 无法确定先行词时，保留原文进入意图分类，不阻塞、不转人工（由分类置信度与 UNKNOWN 既有路径承接）
- 非房源实体指代（价格、楼层、位置等）MVP 尽力消解，失败按上一条降级处理

---

### 4.2 意图识别与路由

**Description：** 系统在指代消解（FR-11）之后，对买家首次消息和重复追问的消解后消息进行意图分类，并根据意图类型决定后续处理路径：缓存应答 / LLM 生成 / 转人工。意图分类是路由的第一道决策门，准确率直接决定后续所有环节的正确性。

**Functional Requirements：**

#### FR-1: 意图分类

系统对 FR-11 输出的每条消解后消息输出一个意图标签（Intent）和置信度分数。

**Consequences (testable):**
- 意图分类准确率 ≥ 90%（基于人工标注的测试集，测试集规模 ≥ 1000 条，覆盖全部 9 类意图，其中含指代改写样本）
- 意图分类延迟 P99 < 50ms（含指代消解的端到端口径，见 FR-11）
- 意图分类结果写入会话状态（Redis），键：`weiliao:session:{session_id}:intent:{turn}`

#### FR-2: 重复追问识别

系统识别同一 session 中针对同一意图的第 2 次及以后的消息，标记为 Follow-up Query。

**Consequences (testable):**
- 重复追问识别准确率 ≥ 95%（同义改写视为同一意图，如"还在吗"与"没卖掉吧"）
- 同一意图判定基于消解后消息：指代与同义改写叠加的场景（"它多少钱"与"这套房多少钱"）视为同一意图
- 追问次数计数器存储于 Redis，TTL 与会话一致（30 分钟）
- 追问次数 ≥ 3 时，无论意图类型，强制触发转人工（Hard Trigger）

#### FR-3: 硬触发转人工

系统命中任一硬触发条件时，立即将会话转交经纪人工作台，同时向买家发送安抚消息。

**Consequences (testable):**
- 红线意图（NEGOTIATION / LOAN_POLICY / COMPLAINT）识别后 100% 转人工，零生成回答
- 图片/语音输入 100% 转人工
- 同一意图追问 ≥ 3 次 100% 转人工
- 转人工消息送达经纪人工作台延迟 P99 < 5s
- 买家在转人工后收到通知："已为您转接经纪人，请稍候"

**Out of Scope:**
- 软触发（基于置信度分数的转人工判断）不在 MVP 范围
- 转人工后的会话历史摘要生成（经纪人工单增强）不在 MVP 范围

---

### 4.3 L0 缓存与事实卡片

**Description：** 系统以"意图 + 房源 ID + 房源状态 + 价格分桶"为 key 缓存事实卡片（房源状态、当前价格、对口学校、上次对话上下文），由消费端（模板引擎或 LLM）在响应组装时引用。缓存的价值是消除 LLM 调用，不是复用最终文案。

**Functional Requirements：**

#### FR-4: 事实卡片缓存

系统维护 L0 缓存，存储单元为事实卡片而非最终应答文案。

**Consequences (testable):**
- 缓存 key 结构：`weiliao:l0:{intent}:{house_id}:{status}:{price_bucket}`
- 事实卡片包含：房源状态（active/sold/offline）、当前挂牌价（分桶到 10 万）、对口学校（如有）、最近 3 轮对话摘要
- 缓存 TTL 5 分钟，房源状态变更（Kafka `house.sync.trigger` 事件）时主动失效
- L0 缓存整体命中率 ≥ 80%（压测验证）

#### FR-5: 重复追问禁走缓存

Follow-up Query 不得命中 L0 缓存，必须进入 LLM 链路。

**Consequences (testable):**
- 同一 session 中同一意图的第 2 次消息 100% 进入 LLM 链路（Langfuse trace 可验证）
- LLM 响应不得与首次缓存响应完全相同（文本相似度 < 0.8）

---

### 4.4 LLM 生成与风控

**Description：** 对未命中缓存且非红线意图的消息，系统调用 OpenAI 生成受控回答。生成前后均须过风控审核，审核不通过时用模板兜底，禁止将未审核内容发给买家。

**Functional Requirements：**

#### FR-6: LLM 受控生成

系统调用 OpenAI（gpt-4o 或 gpt-4o-mini）生成买家响应，prompt 包含事实卡片、对话上下文和生成约束。

**Consequences (testable):**
- 生成内容必须基于事实卡片中的房源数据，不得虚构价格、面积、学区信息
- prompt 中明示生成约束："不得承诺价格可谈、不得承诺学区名额、不得使用'最''第一'等违禁词"
- 生成延迟：首 token 到达 P99 < 1.5s

#### FR-7: 生成后审核机制

系统对 LLM 生成内容执行后置审核，审核不通过时切换至模板兜底应答。

**Consequences (testable):**
- 100% 的 LLM 生成内容须通过风控中台审核后才可发送
- 审核不通过时，买家收到的响应为模板兜底版本，服务无中断
- 审核通过率 ≥ 95%（上线前压测基线，作为全量放行门槛）

#### FR-8: OpenAI 故障降级

OpenAI 返回 429 / 5xx / 超时（> 3s）时，系统自动切换至模板兜底。

**Consequences (testable):**
- OpenAI 不可用期间，服务可用性不降级（不返回 5xx 给买家）
- 降级切换时间 < 100ms
- 降级事件写入 Langfuse trace 并触发监控告警
- OpenAI 恢复后，按 10% 步进逐步切回（避免瞬时流量打挂）

---

### 4.5 AI 身份披露

**Description：** 买家在与 Agent 对话的全过程中，聊天界面必须持续可见"AI 助手"标识。Agent 不得以真人经纪人身份自称。

**Functional Requirements：**

#### FR-9: AI 披露标识

聊天界面在 Agent 响应气泡旁持续展示"AI 助手"标识，转人工后标识消失。

**Consequences (testable):**
- Agent 响应 100% 携带 AI 标识
- 转人工后，标识切换为经纪人姓名/头像，无残留
- Agent 生成的文本中不得包含"我是这套房的经纪人"或等价表述（风控审核范围）

---

### 4.6 会话状态管理

**Description：** 系统维护买家会话状态（意图历史、追问计数、事实卡片引用），保证多轮对话的上下文一致性。会话状态存储于 Redis，所有 Agent 服务实例共享。

**Functional Requirements：**

#### FR-10: 会话状态一致性

同一 session 的连续消息，无论由哪个服务实例处理，均可读取一致的会话状态。

**Consequences (testable):**
- 会话状态存储于 Redis，TTL 30 分钟
- 多实例并发读取同一 session 状态不产生竞态条件（Redis 原子操作或分布式锁）
- 会话过期后重新发起对话，状态从零初始化，无残留

---

## 5. Non-Goals (Explicit)

- 不做议价辅助 Agent（V2+）
- 不做经纪人数字分身（人设模拟、语气克隆）
- 不做多级模型降级链（DeepSeek / Qwen 接入，V2）
- 不做软触发（置信度低于阈值转人工），仅硬触发
- 不做图片/语音理解与生成，此类输入直接转人工
- 不做带看调度、签约材料等后置链路 Agent
- 不承诺业务转化指标（首响时间对带看率的影响由产品团队另行评估）
- 不做跨会话/跨房源的指代消解（会话绑定单一房源，指代范围以会话内为限）

## 6. MVP Scope

### 6.1 In Scope

- 指代消解（房源指代归一化，意图分类前置步骤，FR-11）
- 意图识别（9 类）+ 硬触发转人工规则引擎
- L0 事实卡片缓存（Caffeine 本地 + Redis 分布式，两级）
- OpenAI 单模型受控生成 + 模板兜底
- 风控双审（生成后审核 + 兜底切换）
- AI 身份披露标识
- 语料标注与测试集建设（第 1-2 周启动，第 4 周出初版测试集）
- Langfuse 全链路 trace 与成本追踪

### 6.2 Out of Scope for MVP

| 项目 | 原因 | 目标版本 |
|------|------|----------|
| DeepSeek / Qwen 降级 | 降低 MVP 集成复杂度，先验证 OpenAI 链路稳定性 | V2 |
| 软触发置信度转人工 | 需要置信度标定数据，MVP 阶段无标注基础 | V2 |
| 会话历史摘要（给经纪人） | 增强体验，非首响核心路径 | V2 |
| 图片/语音理解 | 需要多模态模型，技术栈不同 | V3 |

## 7. Success Metrics

**Primary**
- **SM-1**: 首响延迟 P99 < 3s — 从买家消息到达至买家收到响应的端到端耗时。 Validates FR-1, FR-6.
- **SM-2**: 缓存拦截率 ≥ 80% — 命中 L0 缓存（零 LLM 调用）的请求占总请求的比例。 Validates FR-4, FR-5.
- **SM-3**: 服务可用性 99.95% — Agent 服务自身可用性，不含 OpenAI 侧故障（OpenAI 故障由模板兜底承接）。 Validates FR-8.

**Secondary**
- **SM-4**: 意图分类准确率 ≥ 90% — 基于人工标注的 ≥1000 条测试集。 Validates FR-1.
- **SM-5**: 生成内容审核通过率 ≥ 95% — 上线前压测基线。 Validates FR-7.
- **SM-6**: 转人工判定准确率 ≥ 85% — 应转人工而未转（漏转）的比例 < 15%。 Validates FR-3.
- **SM-7**: 转人工延迟 P99 < 5s — 触发转人工到消息送达经纪人工作台。 Validates FR-3.

**Counter-metrics (do not optimize)**
- **SM-C1**: 缓存命中率 — 不追求 > 80%，拦截率达标即可。过度优化缓存命中率会挤占 LLM 应处理的复杂场景，导致体验下降。
- **SM-C2**: LLM 生成占比 — 不以降低 LLM 调用占比为目标。重复追问走 LLM 是刻意的体验设计，用 LLM 占比衡量成本效率而非体验质量。
